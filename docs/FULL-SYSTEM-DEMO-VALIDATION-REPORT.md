## B. Scope, method & environment

**Branch / commit:** `claude/loving-cerf-msihqg` @ `09e05c2`
**Build type:** Production build (`next build` → `next start`), served on
`0.0.0.0:3000` — not a dev server.
**Backend:** Real PostgreSQL (port 5433, DB `lending_e2e`), real PostgREST
(v12.2.3), GoTrue-compatible auth shim — the production data path, not mocks.
**Data:** 100% synthetic. No real client, staff or financial information was
used or created at any point.

**Method.** A fresh teardown + rebuild + reseed was performed to guarantee a
clean environment. Validation then combined four independent evidence
sources:

1. **The full automated test matrix** run against the fresh seed (3,096 tests).
2. **An instrumented Playwright crawl** (`.e2e/validate.mjs`) that signs in as
   each role and visits every route it is expected to use, capturing HTTP
   status, console errors/warnings, unhandled page errors, failed network
   requests and a full-page screenshot per route — plus a mobile/tablet and
   dark-theme subset.
3. **Negative permission probes** — each role deliberately driven at routes it
   must *not* reach, recording the final URL and a content-leak heuristic.
4. **Direct SQL** against the live demo database for the data inventory and
   the financial/integrity reconciliation.

**Not done, by design:** no deployment, no merge, no production target, no
fixes. The run is report-only.

## M. Data consistency & financial reconciliation

Run directly against the live demo database. All invariants hold **exactly.**

| Check | Expectation | Result |
|---|---|---|
| **Global:** Σ posted payments = Σ allocations | equal | **3,602,317 = 3,602,317 ✅** |
| **Per-loan:** posted total = allocated total | 0 mismatches | **0 mismatches ✅** |
| Allocation components sum to `allocated_amount` (principal + interest + penalty) | 0 mismatches | **0 ✅** |
| `total_paid` = `principal_paid` + `interest_paid` (all loans) | always | **0 exceptions ✅** |
| `posted_payment_total` = `total_paid` + `penalty_paid` (all loans) | always | **0 exceptions ✅** |
| Reversed payment excluded from live balances | yes | **✅ (allocation retained for audit only)** |
| Loans with negative outstanding / overpayment | 0 | **0 ✅** |
| `fully_repaid = true` while `outstanding ≠ 0` | 0 | **0 ✅** |
| Orphan loans / payments / allocations | 0 / 0 / 0 | **0 / 0 / 0 ✅** |
| Negative money (principal, expected, payment amount) | 0 | **0 ✅** |

**Note on the one view "difference" that looks like a mismatch but is not.**
One active loan shows `posted_payment_total = 411,892` but `total_paid =
402,500` (gap 9,392). This is **correct by definition**: `total_paid` is the
*contractual* portion (principal + interest), while `posted_payment_total` is
*gross cash* including the `penalty_paid` of 9,392 on that loan. The identity
`posted_payment_total = total_paid + penalty_paid` holds for **every** loan
(0 exceptions), confirming the two columns measure different, consistent
things. No reconciliation defect.

Financial integrity: **clean.**
